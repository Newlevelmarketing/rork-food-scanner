## HIGH

### `ios-calzy/ModernBodyFoodScanner/Services/CameraService.swift:37` — status flips to .running before startRunning() executes, so the shutter is live against a dead session

**Lens:** ios

**Impact.** Verified line-for-line: line 37 assigns status = .running synchronously, line 38 only *queues* session.startRunning() on the serial queue. ScanView.swift:223-224 gates the shutter solely on that flag (.disabled(camera.status != .running || isAnalyzing)), and capture() (line 90) re-checks the same flag before calling output.capturePhoto. So during the sub-second window between the flag flip and the session actually running, the shutter renders at full opacity, enabled, over a black preview, and a tap reaches capturePhoto with no active video connection - the classic uncatchable NSInvalidArgumentException. I also confirmed the second half of the claim independently: grep for NotificationCenter / AVCaptureSessionRuntimeError / WasInterrupted / DidStartRunning / scenePhase across all of ios-calzy returns nothing but ReminderService's UNUserNotificationCenter, so nothing ever drives status back off .running when the session is stopped by an interruption.

**Fix.** Assign .running from inside the queue block after session.startRunning() returns (hopping back to the MainActor), or drive status from .AVCaptureSessionDidStartRunning. Additionally guard capture() on output.connection(with: .video)?.isActive == true, and observe AVCaptureSessionRuntimeError / WasInterrupted / InterruptionEnded.

> **Verification.** Survives, severity lowered critical -> high. The code says exactly what the finding claims and it is not in the unit-17 carried-forward list (progress-tracker.md:123 only notes that the restart path is untested). Downgraded because reaching the crash needs a user tap inside a sub-second window while the preview is still black - a real but not routine trigger - and the Simulator reachability argument in the finding is correct, so this is a device-only defect that has never been exercised.

### `ios-calzy/ModernBodyFoodScanner/Store/AppStore.swift:299` — iOS "Delete All Data" leaves every meal photo and progress photo JPEG on disk

**Lens:** legal-privacy

**Impact.** eraseAll() resets `data = AppData()` and persists, but photos are not in AppData — they are JPEGs written to Documents/images/ (imagesDirectory, line 27; written at line 269 by saveImage). deleteMeal (line 187) and deletePhoto (line 290) each call FileManager.removeItem on that directory; eraseAll does not, and it is the only caller of the destructive Settings action (SettingsView.swift:164). Every meal photo and progress photo therefore survives "Delete everything" as an orphan no code path can reach, and continues into iCloud Backup. Three shipped strings say otherwise: SettingsView.swift:170 confirmation dialog, Legal.swift:113-116 (privacy section 5), and the FAQ at Legal.swift:230. Android (AppViewModel.kt:207 -> mutate { AppData() }) and web (AppStore.tsx:380 -> setData(emptyData)) keep photos inline in the persisted blob, so both genuinely erase; iOS is the sole platform where the promise is false.

**Fix.** In eraseAll(), removeItem then createDirectory on imagesDirectory before persisting the empty AppData, matching the per-item pattern already used by deleteMeal and deletePhoto.

> **Verification.** Verified line by line: AppData (lines 5-12) has no file-backed photo storage, imagesDirectory is created in init and only ever pruned by deleteMeal/deletePhoto, eraseAll's body is exactly the three lines quoted, and both mirror platforms do erase. Severity lowered critical -> high: the orphans stay inside the app's own sandbox, are unreadable by other apps, and go away on uninstall — there is no exfiltration and no user-visible data loss, only a false deletion claim plus indefinite retention of body photos.

### `web/src/components/calzy/Primitives.tsx:281` — Toggle and Slider render controls with no accessible name — 3 switches and every slider are anonymous to assistive tech

**Lens:** ux-a11y

**Impact.** Confirmed by reading Primitives.tsx:271-335. `Toggle` declares role="switch" + aria-checked but accepts no label prop and its only child is a decorative <span> (line 290), so it announces as "switch, off" with no subject. `Slider` (line 299) renders a bare <input type="range"> with no aria-label, no id and no wrapping label. ## MEDIUM

### `android/app/src/main/java/com/rork/calzyandroid/AppViewModel.kt:62` — Debounced save lives on viewModelScope with no flush on onCleared, so the last mutation is lost if the ViewModel dies inside the 260 ms window

**Lens:** android

**Impact.** mutate() (lines 59-70) cancels the previous saveJob and starts a new viewModelScope coroutine that sleeps delay(260) before writing. viewModelScope is cancelled in ViewModel.onCleared(), and there is no onCleared override anywhere in the file (verified: the class ends at line 211). If the activity finishes, or the backgrounded process is killed, within ~260 ms of the last mutation, that write never runs and the mutation is lost from disk with no error. addMeal (line 96, called from MealResultSheet.kt:133) and eraseAll (line 207) are both exposed to this.

**Fix.** Override onCleared() to cancel the timer and write _data.value synchronously, and/or perform the write on an application-scoped / NonCancellable coroutine. A flush on Lifecycle.Event.ON_STOP would also close the process-death window.

> **Verification.** CONFIRMED mechanically: I read lines 44-70 and the whole class; there is no onCleared, no ProcessLifecycleOwner hook, and no application scope. Downgraded critical -> medium: the exposure window is only the 260 ms following a mutation, and only the single most recent write is at risk (the write serialises the whole document, so cancelling earlier debounced jobs is harmless). The original's 'let the OS kill the backgrounded process and the meal is gone' overstates it — any kill more than a quarter second after the last tap has already been persisted.

### `android/app/src/main/java/com/rork/calzyandroid/AppViewModel.kt:54` — load() swallows every decode failure into a fresh empty AppData, and the next mutation overwrites the file with it

**Lens:** android

**Impact.** load() (lines 52-56) is `catch (error: Exception) { AppData() }`. Any failure to parse calzy-data-v1.json — truncated file, a schema change that breaks a non-defaulted field, disk error — makes the app come up as a clean first-run install (hasOnboarded false, so AppNavigation.kt:59 routes to onboarding). The user is never told, no copy of the bad file is kept, and the first subsequent mutate() writes the empty AppData over the original at line 65, making the loss permanent. store.writeText is also a truncate-then-stream, so a kill mid-write can produce exactly the truncated file this catch then discards.

**Fix.** On a decode failure, move the unreadable file aside (…​.corrupt) and surface an error state instead of silently returning AppData(); refuse to overwrite until acknowledged. Write via a .tmp file plus renameTo so a partial write can never replace a good document.

> **Verification.** CONFIRMED: I read the catch and the write. Downgraded critical -> medium. The 'killed mid-write' half is the weaker leg — the write runs on Dispatchers.IO while the app is typically foregrounded and takes tens of ms — but the silent-reset-then-overwrite path is real for any decode failure, not just torn writes, and that is what makes it unrecoverable. Distinct from known issue #2 (web localStorage quota): that is a silent *write* failure on web, this is a silent *read* failure plus destructive overwrite on Android.

### `android/app/src/main/java/com/rork/calzyandroid/ui/sheets/ScanSheet.kt:330` — Capture and gallery import run full-resolution decode, rotate, JPEG encode and base64 on the main thread

**Lens:** android

**Impact.** takePicture is given ContextCompat.getMainExecutor (line 330), so onCaptureSuccess (lines 332-337) runs on the UI thread and does image.toBitmap(), ImageUtils.rotate (which allocates a second full-resolution bitmap, ImageUtils.kt:74-78) and ImageUtils.bitmapToDataUrl (scale + Bitmap.compress + Base64.encodeToString, ImageUtils.kt:20-38) before scope.launch is ever reached. > **Verification.** CONFIRMED: read ScanSheet.kt:326-343, ImageUtils.kt in full, ProgressScreen.kt:108-116. Downgraded high -> medium: the outcome is shutter jank and OOM risk, not the 5-second ANR the original implies, and the ImageProxy-leak leg is weaker than claimed — an exception thrown out of onCaptureSuccess on the main executor crashes the app rather than quietly stalling the pipeline.

### `ios-calzy/ModernBodyFoodScanner/Store/AppStore.swift:43` — persist() spawns an unordered detached write per mutation; paired mutations can commit the older snapshot last

**Lens:** ios

**Impact.** Confirmed: persist() (lines 43-51) copies `data` then fires an independent Task.detached that encodes and writes to the same fileURL. Nothing serializes the tasks. All three cited pair-of-mutations call sites are real - ProgressDashboardView.swift:678-679 (store.profile = profile; store.logWeight(...)), SettingsDetailViews.swift:255-256 (identical pair), OnboardingView.swift:417-418 (store.profile = profile; store.completeOnboarding(), the latter seeding the first WeightEntry at AppStore.swift:77-79). If the first task's write lands last, the file on disk lacks the weight entry. Writes are .atomic so there is no torn file, only a stale one.

**Fix.** Funnel snapshots through a single serial consumer (an actor or one serial queue owning the file), and/or debounce-and-coalesce so only the newest snapshot is written.

> **Verification.** Survives, severity lowered high -> medium. **Fix.** Keep a module-level stack of open sheets and let only the top-most instance act on Escape, or have the consuming handler call event.stopPropagation().

> **Verification.** Confirmed both sheets are simultaneously open (EditMealSheet returns null before rendering the sheet only while meal is null, MealDetail.tsx:51 passes open unconditionally) and both listeners are on window. Downgraded medium -> low: keyboard-only path in a mobile-first app, recoverable by reopening the meal.

### `web/src/features/ShareSummary.tsx:35` — ShareSummary keeps its error message across close and reopen

**Lens:** web-logic

**Impact.** The !open branch of the effect resets `ready` only; `error` is cleared solely inside share() (line 62). ShareSummary is mounted persistently by Home (pages/Home.tsx:144) rather than conditionally, so the state survives a close. After a drawSummaryCard rejection or a non-AbortError share failure, reopening the sheet shows "Sharing failed. Try again." (or "Couldn't build your summary card.") above the action button while a perfectly good card renders behind it, before anything has been tried.

**Fix.** Add setError(null) alongside setReady(false) in the !open branch, matching ScanSheet, DescribeSheet, SearchSheet and ExerciseSheet.

> **Verification.** Read the whole file plus the Home mount point; the component is never unmounted, so state genuinely persists. Kept at low — cosmetic and self-correcting on the next successful share.

### `web/src/pages/Home.tsx:247` — Home's carousel page dots are hard-wired to page 0 and never update

**Lens:** web-logic

**Impact.** A repo-wide grep for setPage returns exactly two hits: the useState at Home.tsx:51 and the onFocus at Home.tsx:247, which sets the value the state can already only hold. The second snap panel (line 274) has no handler, and there is no scroll listener or IntersectionObserver anywhere in web/src. Swiping to the Burned/Weight/Health panel leaves the first dot wide and dark and the second small and faint, so the indicator permanently misreports which page is showing.

> **Verification.** Verified by reading lines 242-315 and grepping setPage/onScroll/IntersectionObserver across web/src — two hits, both as described. Downgraded medium -> low: purely a cosmetic indicator; the carousel itself scrolls fine and no data is affected.

## Spot-checks

### Shared data assets — CLEAN, no follow-up needed
`foods.json` and `strings.json` are byte-identical across all three platforms (md5 `9488389a…` and `dbf6a363…` for web/`src/data`, android/`assets`, ios/`Resources`). ### Localization coverage — WARRANTS A FOLLOW-UP PASS
The 52-key table is a facade over a mostly hard-coded English app. Measured:

- **Web:** `t("…")` appears 26× in `Settings.tsx`, 15× in `Home.tsx`, once each in `ShareSummary.tsx` and `DescribeSheet.tsx`, and **0 times** in `Onboarding.tsx`, `Progress.tsx`, `ScanSheet.tsx`, `MealResult.tsx`, `EditMealSheet.tsx`, `ExerciseSheet.tsx`, `SearchSheet.tsx`, `Paywall.tsx`. Example literals: `web/src/pages/Onboarding.tsx:104` `title="First, the basics"`, `:287` `"Start tracking"`.
- **iOS:** 53 hard-coded `Text("…")` literals, e.g. `Views/DescribeMealView.swift:26` `"Describe what you ate"`, `Views/EditMealSheet.swift:192` `"Save changes"`.
- **Android:** 76 hard-coded `text = "…"` literals, e.g. `ui/screens/OnboardingScreen.kt:166` `"What should we call you?"`, `:522` `"Point your camera at any meal.\nWe'll do the counting."`.

Compounding it: dates follow the *device* locale, not the in-app choice, on all three (`web/src/lib/dates.ts:37` `toLocaleDateString(undefined, …)`, `Views/Components/DateStrip.swift:46` `.formatted(…)`, `data/Dates.kt:43` `Locale.getDefault()`). A user selecting Polish gets a Settings screen in Polish, an onboarding flow and scan flow in English, and English weekday names. This is a store-listing accuracy problem adjacent to the legal findings already logged, and it is invisible to every lens that ran.

### Native accessibility — WARRANTS A FOLLOW-UP PASS
The web lens found anonymous switches and sliders. Both native apps have the same defect and no lens looked:

- **Android:** `ui/components/Primitives.kt:127` — the app-wide `Pressable` wrapper builds every tappable from `Modifier.clickable(…)` with no `role = Role.Button` and no `onClickLabel`; TalkBack announces its children as plain text. The segmented control at `Primitives.kt:269` likewise uses bare `clickable` with no `selectable`/`Role.RadioButton`, so selected state is inaudible. `CalzySlider` (`:297`) and `Switch` (`:318`) take no `contentDescription` or `stateDescription` parameter at all, and there are 20 call sites. Across the entire Compose source there are exactly **3** references to `semantics`, all on one line (`ProgressScreen.kt:981`), and 49 of 77 `contentDescription`s are `null`.
- **iOS:** 10 accessibility modifiers in the whole app, against **273** `.font(.system(size:))` calls. Fixed-point `.system(size:)` does not scale with Dynamic Type, so text size is frozen app-wide regardless of the user's setting.

### iOS packaging and Android permissions — CLEAN
Checked because nothing covered them. `project.pbxproj:405-412` carries honest, specific `NSCameraUsageDescription`, `NSPhotoLibraryUsageDescription` and `NSPhotoLibraryAddUsageDescription`, `ITSAppUsesNonExemptEncryption = NO`, iPhone portrait lock. `AndroidManifest.xml` requests only `INTERNET` and `CAMERA`, marks camera `required="false"`, keeps the FileProvider `exported="false"` and scopes it to `cache/share/` only. Aside from the already-known placeholder bundle id and the already-reported `allowBackup`, this surface is fine.
